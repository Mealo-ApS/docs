Dully · POS integration

Outpost order integrationReceiving Dully orders, and reporting back

Dully sends an event to Outpost when an order is approved, and another when it is cancelled. Outpost signs each one and delivers it to your endpoint. Every approved order includes a URL you can post to with your own order reference.

This page documents what arrives, how to verify it, and the callback you send. Fields that are not listed here are not sent.

Overview

How it works

There are two things to build.

Receive order events

Outpost posts to your endpoint for each restaurant you are subscribed to, following the Standard Webhooks spec. The topic arrives in the webhook-topic header, and the body is the order data on its own.

TopicSent whenBody
order.approvedThe order is paid and confirmed by the restaurant.A schema.org Invoice with the full order.
order.cancelledAn order you already received is cancelled.The order id and its new status.

Post the callback

Every approved order carries a callbackUrl. Post your order id, receipt id, print state or error to it. The values appear on the order in Dully, where restaurant staff and support can see them. It is optional, but without it nobody on the Dully side can tell whether the order reached your POS.

Responding to a delivery

Answer with any 2xx status. Verify the signature, store the event, and respond; do the POS work afterwards rather than holding the connection open.

Anything other than 2xx, or no response at all, counts as a failed attempt and Outpost retries with exponential backoff. Defaults are ten attempts with a 30 second base interval, and the operator can change both. A retry reuses the same event id. Once attempts are exhausted the event can still be redelivered by hand from the Outpost portal.

Handle repeat deliveries

Delivery is at-least-once, so the same event can arrive more than once. Use webhook-id as your idempotency key and ignore an event you have already processed.

Security

Authentication

An order passes through three systems, and each hop is authenticated differently. Only the last one is yours to handle.

HopHow it is authenticatedYour part
Dully → Outpost A bearer token that Dully holds for the Outpost API. Nothing.
Outpost → your endpoint A Standard Webhooks signature in the webhook-signature header. Verify every delivery. This is the important one.
Your callback → Dully A signed token inside the callbackUrl. Post to the URL as you received it.

Dully issues you no API key and runs no OAuth flow. You hold one long-lived secret, the Outpost signing secret for your endpoint, and one short-lived token per order that arrives inside the payload.

Verifying a delivery

Your endpoint is a public URL, so the signature is the only thing separating a real order from anything else that reaches it. Verify every delivery and reject anything that does not match.

Deliveries are signed according to Standard Webhooks. The signature is an HMAC-SHA256 over webhook-id.webhook-timestamp.body, base64 encoded, sent as webhook-signature: v1,<signature>. Your secret looks like whsec_….

Do not implement this by hand. Standard Webhooks publishes verification libraries for most languages that handle the signing, the constant-time comparison and the timestamp tolerance for you. Pass them the raw request body, before any JSON parsing, and your secret.

  • Standard Webhooks — the spec and the verification libraries.
  • Outpost webhook signatures — how Outpost applies the spec, including secret rotation.

The secret is generated when your endpoint is registered and is shown in the Outpost tenant portal, which is also where you rotate it. During a rotation window webhook-signature carries a space-delimited list with one signature per valid secret, so accept the delivery if any of them matches. The libraries already do this.

The callback token

The t query parameter on callbackUrl is a JSON Web Token signed with HMAC-SHA256. Dully holds the signing key, so you cannot mint or alter a token, and you do not need to verify one. Post the URL back unchanged.

Decoding it is useful when you are debugging. The claims are not secret, but the signed token is:

ClaimMeaning
orderIdThe order the token is for. Matches webhook-id.
storeIdInternal store reference Dully uses to load the order. Nothing you need to act on.
expExpiry, set two hours after the order is due. Call back well before this.

Handling it

  • The URL is the credential. Anyone holding it can write callback fields to that order, so keep it out of shared logs, error reports and anything a client can read.
  • One token per order. It authorises the callback fields on that single order and nothing else. It grants no read access and no access to any other order.
  • Send it byte for byte. Re-encoding, trimming or rebuilding the query string invalidates the signature and the callback is refused with 401.
  • Drop it when you are done. Keep it alongside the order until you have called back, then discard it. There is no way to renew a token.

Reference

What arrives

A delivery is a POST with the order data as the body. Everything about the event itself is in the headers, so read the topic from webhook-topic rather than looking for it in the JSON.

HeaderExampleMeaning
webhook-ide4b5e2ff-…The order id. Stable across retries and identical in the approved and cancelled events. Deduplicate on this.
webhook-timestamp1770813296Unix timestamp in seconds for the delivery attempt. Part of the signed content, and what you check against your replay tolerance.
webhook-signaturev1,K5oZfzN95Z9…The signature. See Authentication.
webhook-topicorder.approvedWhich event this is. Also order.cancelled.
webhook-sourcedullyAlways dully.
content-typeapplication/jsonThe body is JSON.

Match header names case-insensitively. webhook-timestamp is the time of the attempt, not of the order, so it changes on a retry while webhook-id stays the same.

No restaurant id in the delivery

The body carries the restaurant's name and address under seller, but not its Dully id, and there is no tenant header. If you serve more than one restaurant, register a separate endpoint per restaurant so you can tell them apart by the URL that was called.

Event

order.approved

The body is a schema.org Invoice. It holds the order id, the order itself under referencesOrder, and the amount charged under totalPaymentDue.

Order lines

Each entry in acceptedOffer is an Offer. The entries with a Product are what the customer bought. The last entry is the handling fee and is described in the next section.

FieldPresenceMeaning
pricealwaysLine total with VAT. Quantity, options and discounts are already applied.
priceCurrencyalwaysISO currency code, for example DKK.
eligibleQuantityalwaysQuantitativeValue holding the quantity.
priceSpecificationalwaysUnit price with VAT, options and discounts already applied.
itemOfferedalwaysProduct: name, category, productID, sku, and an absolute image URL when the product has one.
addOnconditionalOptions and modifiers chosen for this line. Each is an Offer with the same fields. Add-ons carry no product image.
additionalPropertyconditionalSent only when the customer wrote a note on this line: a single customerComment property.
Reading prices

priceSpecification is the unit price with VAT, including the options on that line and its share of any discount. A 5.00 burger with 8.00 of toppings and 1.00 off arrives as a unit price of 12.00, and three of them as a line price of 36.00.

The addOn prices are shown separately for display, so do not add them on top of the parent line when you calculate a total. Use totalPaymentDue.price for the amount charged.

The last offer in acceptedOffer is always the handling fee: itemOffered is a Service named Handling fee, and price is the fee with VAT. Its additionalProperty array carries the order details that schema.org has no field for.

Names can repeat

discountCode and giftCard appear once per code or card, so read additionalProperty as a list and group by name. Building a dictionary of unique keys will drop values.

Money

Discounts & gift cards

Dully has several ways to reduce what a customer pays. Only some of them come with a code.

KindCode in the payloadEffect
Discount and campaign codes Yes. referencesOrder.discountCode, and one discountCode property per code. Lowers line prices and the total.
Gift cards Yes. One giftCard property per card, with the code and the redeemed amount in the same node. Lowers the amount due.
Vouchers, member cards, stamp cards, loyalty rewards No. Lowers line prices and the total, with no code to report.

To reconcile a total: priceBeforeDiscount minus totalPaymentDue.price is everything that was taken off, whether or not it has a code. referencesOrder.discount gives the discount total on its own.

Event

order.cancelled

Sent when an order you already received is cancelled, usually because the restaurant rejected it. The body is the order id and its new status.

The id matches the identifier on the invoice you already received, so it maps straight onto that order.

Void the whole order

Dully puts back everything the order used: gift card balances, vouchers, stamps and single-use discount codes are all restored, so a one-time code becomes usable again. Cancel the order in full on your side rather than partly unwinding it.

You send

Order callback

Take the callbackUrl from the handling fee properties and post to it. Send the URL exactly as you received it, including the query string. Do not rebuild or re-encode it.

POST{callbackUrl}

The t parameter in the URL authenticates the call, so no header credential is needed. See Authentication for what it contains and how to handle it. Send Content-Type: application/json.

Request

Every field is optional. Send what you have, and post again later when you know more. Field names are matched case-insensitively.

FieldTypeMeaning
externalOrderIdstringYour order id. Shown to Dully staff and support as the POS reference.
externalTransactionIdstringYour transaction or receipt id.
posPrintedstringWhether the ticket printed.
statusstringHow the order ended up in your system.
errorstringWhat went wrong, if something did.

Extra keys are accepted rather than rejected, so a richer body will not fail. Only the fields above are stored on the order.

Response

All responses use the same envelope. isUpdated is false when the body held nothing to store; the call still succeeded.

StatusMeaningWhat to do
200Accepted and processed.Nothing. Check data.isUpdated to confirm something was stored.
400The t parameter or the body is missing, or the token does not identify an order.Do not retry unchanged. The URL was altered or the body was empty.
401The token failed validation.Do not retry. Use the callbackUrl exactly as delivered.
404The order no longer exists.Stop.
500Callbacks are not enabled for this site.Retry later and let Dully know.
Safe to repeat

The callback overwrites the fields it receives, so posting the same body twice is harmless and a later status replaces an earlier one.

Reference

Parsing rules

  • Empty values are removed. Nulls are stripped from the payload and empty arrays are left out. Treat every field as optional unless this page says it is always sent.
  • Text is UTF-8 and unescaped. Danish and other national characters arrive as themselves, not as escape sequences.
  • Money is a JSON number in major units, never a string and never in cents. 1.95 means 1.95 in the order's currency.
  • pickupTime is UTC with milliseconds and a Z suffix. orderDate and expectedArrivalFrom are ISO-8601 and may carry a local offset instead, so parse the offset rather than assuming UTC.
  • Types are schema.org. Each object carries an @type, and enum-style values are full schema.org URLs such as https://schema.org/OrderProcessing.
  • New fields can appear. Ignore what you do not recognise instead of failing the payload.
